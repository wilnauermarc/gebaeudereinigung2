# Objektia

> **Stand: Frontend-Prototyp mit erstem Server-Teil.** Anmeldung, Rollen und Datenspeicherung laufen jetzt auf dem Server (SQLite, Datei `data/resch.db`). Die Daten in der Demo sind weiterhin erfunden.

## Betrieb mit Docker

`Dockerfile`, `docker-compose.yml` (mit Caddy für https) und `scripts/backup.mjs` liegen im Projekt. Anleitung, Anbieter-Empfehlung und Sicherung: [`docs/betrieb.md`](docs/betrieb.md). Das Image wurde gebaut und der komplette Sicherheitstest (110+ Prüfungen) lief **durch Caddy über https** erfolgreich, dazu Neustart, Sicherung und Healthcheck. Die Ersteinrichtung auf einem Server ist durch einen **Einrichtungscode** (`SETUP_TOKEN` in der `.env`) geschützt. **Nicht getestet:** der Betrieb hinter Caddy mit echtem Zertifikat auf einem Server.

## Anmeldung und Zugriffsschutz

- **Erster Start:** `/login` zeigt die Ersteinrichtung (Konto der Inhaberin, Passwort mindestens 12 Zeichen, Start leer, mit Demo oder mit den bisherigen Browserdaten). Danach ist die Einrichtung gesperrt.
- **Weitere Administratoren und Verwaltungs-Zugänge:** Einstellungen → Zugänge → „Zugang anlegen“ → Art: **Administrator** (voller Zugriff, verwaltet auch Zugänge), **Büro** oder **Objektleitung** (beide sehen alle Geschäftsdaten, können aber keine Zugänge der Verwaltung anlegen oder ändern). Nur Administratoren dürfen Verwaltungs-Zugänge anlegen, zurücksetzen, sperren oder löschen; den eigenen Zugang kann man dort nicht sperren oder löschen, und der **letzte aktive Administrator** lässt sich nicht sperren oder löschen. Neue Zugänge bekommen einen Einmal-Code und müssen beim ersten Anmelden ein eigenes Passwort wählen. Im Sicherheitstest geprüft (Büro darf keinen Administrator anlegen, neuer Administrator muss Passwort wählen und kann danach arbeiten). Die Oberfläche (Auswahlfeld) habe ich nicht im Browser angesehen.
- **Mitarbeitende:** Einstellungen → Zugänge → „Zugang anlegen“ erzeugt einen Anmeldenamen und einen **Einmal-Code** (10 Zeichen, nur einmal sichtbar). Beim ersten Anmelden wählt die Person ein eigenes Passwort (mindestens 8 Zeichen). Mitarbeitende landen nach der Anmeldung ausschließlich auf `/mitarbeiter`.
- **Mitarbeiter-App (`/mitarbeiter`, fürs Handy):** Ein- und Ausstempeln in zwei Taps (Einsatzort nur aus den eigenen Einsätzen des Tages, Zeit ist die **Serverzeit**, Pause beim Ausstempeln), **Krank melden** (Verwaltung bekommt sofort eine Aufgabe „Vertretung klären“, der Springer-Ablauf greift), **Urlaub beantragen** (landet in der Freigabe im Team), **Mangel melden mit Foto** (wird verkleinert, auf dem Server als Bild geprüft, nur für die Verwaltung abrufbar), eigene gebuchte Zeiten mit Hinweisen „beim Büro eingegangen / vom Büro geändert / ungültig“, Objekthinweise und Reinigungsmittel. **Ohne Netz** werden Stempelungen und Meldungen auf dem Gerät gespeichert und nachgesendet (nachgereichte Zeiten werden gekennzeichnet, höchstens 36 Stunden alt). Sprachen: Deutsch, English, Français, Polski, Română, Türkçe (Übersetzungen sind Entwürfe).
- **Eingang statt Direktzugriff:** Mitarbeitende schreiben nie in den Datenbestand der Verwaltung, sondern in einen getrennten Eingang. Die Verwaltung übernimmt ihn alle 30 Sekunden (und bei Fokus) als Zeitbuchung, Abwesenheit bzw. Mangel; jede Übernahme ist über die Eingangs-ID doppelt-sicher. Das vermeidet Konflikte beim Speichern.
- **QR-Stempeln am Objekt:** Beim Kunden unter Objekte → „Stempel-QR“ erzeugt die App einen Aushang (DIN A4) mit geheimem Schlüssel je Objekt. Mitarbeitende scannen ihn mit der Handy-Kamera, melden sich an (der Link wird über die Anmeldung hinweg gemerkt) und stempeln mit einem Tipp. Einstellungen → Stempeln: „Einstempeln nur per QR-Code“ macht den Scan zur Pflicht (belegt Anwesenheit ohne Standortdaten); Ausstempeln geht auch ohne Scan. Der Server prüft den Schlüssel in konstanter Zeit, Mitarbeitende sehen ihn nie, „Neuen Code erzeugen“ macht alte Aushänge ungültig. Ein weitergegebenes Foto des Aushangs ist ein Schwachpunkt (siehe Hinweis auf dem Poster).
- **Schichttausch:** In der Mitarbeiter-App gibt eine Person einen eigenen künftigen Einsatz ab (heute nur bis 3 Stunden vor Beginn, höchstens 5 offene Angebote). Kolleginnen und Kollegen sehen nur Angebote, die sie **übernehmen dürfen**: nicht schon am Objekt eingeplant, nicht abwesend, keine Überschneidung, 11 Stunden Ruhezeit zum Vor- und Folgetag, Minijob-Grenze. Wer zuerst übernimmt, bekommt das Angebot (atomar). Danach entscheidet das Büro im Team („Tauschwünsche“, auch Hinweis auf Heute); beim Genehmigen prüft der Server noch einmal gegen den aktuellen Plan. Der Tausch erscheint im Einsatzplan als Vertretung, die die abgebende Person **ersetzt** (sie gilt an diesem Tag nicht mehr als eingeplant, Besetzung, Prognose und Lücken-Detektor rechnen damit). Mitarbeitende sehen nur Vorname, Zeit und Objekt der Angebote.
- **Standort-Abgleich beim Stempeln (optional, standardmäßig aus):** Einstellungen → Stempeln. Nur im Moment des Ein- und Ausstempelns fragt das Handy den Standort einmal ab; der Server vergleicht ihn mit der Objektposition (Karte) und dem Radius (Standard 150 m, Messungenauigkeit zählt zugunsten der Person) und speichert **nur das Ergebnis** (in Ordnung / ca. X m entfernt / zu ungenau / nicht übermittelt), **keine Koordinaten, kein Bewegungsverlauf**. Es ist ein Hinweis als Notiz an der Zeitbuchung und **sperrt nie** das Stempeln. Die Mitarbeiter-App erklärt das vor dem Stempeln. Getestet: Abgleichslogik (Vitest) und der Ablauf gegen den echten Server (Sicherheitstest: nicht gesperrt, nur Ergebnis gespeichert, bei ausgeschaltetem Schalter nichts gespeichert). **Nicht getestet:** die Standortabfrage im echten Handy-Browser und die Genauigkeit in Gebäuden (GPS ist drinnen oft ungenau; dann steht „zu ungenau“). Rechtlich: Betriebsrat (§ 87 Abs. 1 Nr. 6 BetrVG), Information der Beschäftigten, Verarbeitungsverzeichnis, Datenschutz-Folgenabschätzung prüfen lassen; das ist keine Rechtsberatung. Offline gestempelte Orte liegen bis zum Senden kurz in der Warteschlange des Geräts.
- **Korrekturworkflow für Zeiten:** In der Mitarbeiter-App kann jede eigene Buchung der letzten 14 Tage mit „Korrektur melden“ beantragt werden (neuer Beginn/Ende/Pause plus Begründung). Die Zeit ändert sich nicht sofort: Der Antrag geht ins Büro (Aufgabe, Bereich „Korrekturanträge“ auf der Seite Zeiten, zeigt alt → neu und Begründung). Freigeben schreibt die neuen Zeiten in die Buchung und ins Änderungsprotokoll (wer, wann, alt → neu, Grund); Ablehnen verlangt eine Antwort, die die Person in der App sieht. Abgeschlossene Monate bleiben gesperrt (online kein Antrag, im Büro erst entsperren). Pro Buchung nur ein offener Antrag, Obergrenze 5 Anträge/Stunde. Getestet: Server-Ablauf im Sicherheitstest (Validierung, Fremdbuchung, Doppelantrag, Monatssperre, Sichtbarkeit der Entscheidung) und Freigabe in der Verwaltung im Browser (Buchung + Protokoll geprüft). **Nicht im Browser getestet:** der Dialog in der Mitarbeiter-App; die Übersetzungen sind Entwürfe. Noch offen: Benachrichtigung der Person bei Entscheidung (sie sieht sie beim nächsten Öffnen), Korrektur nach Lohnexport als eigener Nachtragsfall.
- **Monatsabschluss mit Prüfliste und Protokoll:** Auf der Seite Zeiten prüft „Monat abschließen“ vorher: **offene Korrekturanträge des Monats verhindern den Abschluss**; Hinweise (Monat noch nicht zu Ende, eingeplante Einsätze ohne Buchung, Tage über 12 Std., Überschneidungen, Buchungen an Urlaubs-/Krankheitstagen, Buchungen mit Prüfhinweis) lassen sich nach ausdrücklicher Bestätigung übergehen. Danach sind Buchungen des Monats gesperrt. **Entsperren verlangt einen Grund**; Abschluss, Entsperren (mit Grund, Name, Zeit) und jeder Lohnexport stehen im Abschlussprotokoll des Monats. Wurde seit dem letzten Abschluss schon ein Lohnexport erzeugt, warnt der Entsperr-Dialog, dass Änderungen der Lohnbuchhaltung nachzumelden und der Export neu zu erzeugen ist. Getestet: Prüflogik (Vitest) und Abschließen/Entsperren im Browser (Sperre des Buttons, Pflichtgrund, Protokoll). Nicht gebaut: getrennte Zeitstände (erfasst/freigegeben/abrechenbar), Nachtragsbuchung nach Export als eigener Beleg, Rechtekonzept „nur Inhaber darf entsperren“.
- **Übersichtliches Menü:** Oben stehen die vier täglichen Seiten (Heute, Aufgaben, Fristen, Cockpit), darunter fünf Bereiche nach Arbeitsablauf (Verkauf, Einsatz & Team, Qualität, Geld, Ausstattung) als Ziehharmonika: Es ist immer nur ein Bereich offen, nämlich der der aktuellen Seite; zugeklappte Bereiche zeigen die Summe ihrer Warn-Zähler. Mit dem Stern an jedem Eintrag lassen sich bis zu 6 Favoriten oben anheften (nur im Browser gespeichert). Rollen und Basismodus blenden weiter Einträge aus, Tastenkürzel („g“ + Buchstabe) und die Suche (⌘K) bleiben. Im Browser geprüft (Handy-Breite, Bereiche öffnen/schließen, Favorit setzen); die breite Desktop-Ansicht und Tastaturbedienung nicht gesondert.
- **Ablauf im Zentrum (Flow je Vorgang):** Jeder Vorgang ist eine Zeile mit den 8 Schritten (Anfrage → Daten → Besichtigung → Angebot → Rückmeldung → Start → Ausführung → Projektzeitliste) als Kette: erledigte Schritte gelb mit Haken, der aktuelle Schritt groß mit Leuchtring, überspringbare Schritte gestrichelt, noch folgende Schritte ausgegraut, beendete rot. So sieht man auf einen Blick, wer wo steht. Die Spaltenköpfe zeigen, wie viele Vorgänge an welchem Schritt stehen, und filtern per Klick (auch per Link `/vorgaenge?schritt=…`). Auf der Startseite „Heute“ stehen bis zu acht laufende Vorgänge als Flow; dort zählen die Spaltenköpfe genau die gezeigten Zeilen. Zeile anklicken öffnet den Vorgang. Die Zustände werden aus den Vorgangsdaten abgeleitet. Im Browser auf Desktop-Breite geprüft; auf dem Handy scrollt die Kette seitlich (nicht gesondert geprüft). Nicht enthalten: Verweildauer je Schritt und Erinnerung bei Stillstand.
- **Neue Optik (Sonnengelb):** Gelb (#ffc41a, Schrift darauf dunkel für Kontrast) ist jetzt die Primärfarbe; Signalorange, Stahlblau, Petrolgrün und eine eigene Farbe bleiben in den Einstellungen wählbar. Ältere gespeicherte Orange-Voreinstellungen werden einmalig auf Gelb umgestellt. Dazu: warmes Hellgrau mit sanftem Glanz, größere Kartenradien und weichere Schatten, fast schwarze Seitenleiste mit gelbem Logo, gelbem Aktiv-Balken und -Icon, helle Kopfleiste mit Unschärfe-Effekt, Kennzahlen als einzelne Karten, der Ablauf als Stepper mit gelben Zähler-Punkten und Verbindungslinie. Im Browser geprüft: Heute, Vorgänge, Kunden, Einsatzplan, hell und dunkel, Handy-Breite. **Nicht einzeln durchgesehen** sind die übrigen Seiten (sie erben die neuen Farben und Karten über das Design-System); bitte stichprobenartig prüfen, besonders feste Farben in Karte, Kalkulator-Diagrammen und PDFs.
- **Aufräumen nach dem Test-Durchgang:** Einstellungen sind in vier Reiter geteilt (Betrieb · Zugänge & Stempeln · Aussehen · Daten & Datenschutz; `/einstellungen#zugaenge` öffnet den passenden Reiter). Die Seitenleiste hat unten nur noch eine schmale Icon-Leiste (Einstellungen, Rundgang, Designsystem, Hell/Dunkel, Abmelden), sodass alle Bereiche sichtbar bleiben. Der Hinweis „Demodaten“ in der Kopfleiste erscheint nur noch, solange erfundene Daten drin sind (Kennzeichen `settings.demo`, bei älteren Beständen am Platzhalter-E-Mail der Firmendaten erkannt). Caddy setzt nur noch HSTS (die übrigen Sicherheits-Header kommen von der App, vorher doppelt) und leitet `www.<Domain>` auf die Hauptadresse weiter (bei einer Subdomain diesen Block in der `Caddyfile` entfernen). Geprüft: 138 Sicherheitschecks, 110 Tests, Browser (Reiter, Hash, Icon-Leiste, Hinweis). Nicht umgesetzt: Content-Security-Policy; Vorgänge auf der Kundenseite; einheitliche Benennung Cockpit.
- **Leistungsverzeichnis (LV) je Objekt:** Kunde → Objekt → „Leistungen“. Je Raum/Bereich eine Leistung mit Intervall (an jedem Einsatz, wöchentlich … jährlich, nach Bedarf) und optional Fläche. Das LV hat **Versionen mit Gültigkeitsdatum**: Eine neue Version startet als Kopie des bisherigen Stands, muss nach der letzten beginnen und zeigt, was neu, entfallen oder geändert ist. Eine Version, nach der schon Einsätze geprüft wurden, ist gesperrt (Änderungen nur über eine neue Version), damit sich nichts rückwirkend ändert. Die Demo-Daten bringen Beispiel-LVs mit.
- **Leistungsnachweis** (Qualität → Leistungsnachweis): je geplantem Einsatz drei getrennte Zustände: **Anwesenheit** (aus den Zeitbuchungen abgeleitet), **Ausführung** (vollständig / teilweise mit Auswahl der nicht erbrachten LV-Leistungen / nicht ausgeführt, mit Pflichtgrund) und **Abnahme** durch den Kunden (abgenommen / beanstandet, mit Name und Pflichtbegründung; eine Beanstandung legt auf Wunsch einen Mangel mit Nachkontrolle an). Abnahme geht erst nach festgehaltener Ausführung; wird die Ausführung zurückgenommen, entfällt die Abnahme. Jeder Nachweis merkt sich die gültige LV-Version und führt einen Verlauf. Filter (ungeprüft, Abnahme offen, beanstandet), Massenaktion „als vollständig“ für Einsätze mit Zeitbuchung, CSV-Export.
- **Checkliste in der Mitarbeiter-App:** Am Einsatz sieht die Person die Leistungen des Objekts aus dem Leistungsverzeichnis (heute fällige zuerst, periodische unter „Weitere Leistungen“), hakt ab, schreibt optional eine Notiz und macht ein Foto. Der Server nimmt nur Leistungen des Objekts für einen heutigen eigenen Einsatz an (Wiederholung mit gleicher ID ist harmlos, funktioniert auch offline über die Warteschlange). Die Verwaltung übernimmt daraus die **Ausführung** im Leistungsnachweis (alle fälligen abgehakt = vollständig, einige = teilweise mit den fehlenden Leistungen, keine = nicht), mit Hinweis „gemeldet von …“, Foto und einer Aufgabe zur Prüfung bei Abweichung.
- **Fällige periodische Leistungen als Aufgaben:** Für Leistungen mit Intervall monatlich bis jährlich entsteht eine Aufgabe „Fällig: …“, sobald sie in 7 Tagen fällig oder überfällig ist (je Leistung höchstens eine offene). Grundlage ist der letzte Einsatz, an dem sie als erledigt festgehalten wurde (Mitarbeiter-Checkliste oder „Periodische Leistungen, heute miterledigt“ im Nachweis); ohne Nachweis zählt der Beginn des Leistungsverzeichnisses. Achtung: **Beim ersten Lauf** entstehen so für alle bereits überfälligen Leistungen Aufgaben auf einmal.
- **Leistungsnachweis als PDF** (Leistungsnachweis → Objekt wählen → PDF): Monatsnachweis je Objekt für den Kunden mit vereinbarten Leistungen, Einsätzen (Anwesenheit, Ausführung, nicht Erbrachtes, Abnahme) und Unterschriftsfeld.
- **Abnahme durch den Kunden per Link:** Kunde → Objekt → „Abnahme-Link“ erzeugt einen Link mit geheimem Schlüssel (und QR-Code); „Neuer Link“ macht den alten ungültig. Die Kundenseite `/abnahme/<Objekt>?t=<Schlüssel>` braucht keine Anmeldung, zeigt nur dieses Objekt und nur Tage mit festgehaltener Ausführung (mit Nicht-Erbrachtem), keine Namen von Mitarbeitenden, keine internen Notizen, keine Preise. Der Kunde nimmt ab oder beanstandet (mit Text); die Entscheidung landet im Eingang der Verwaltung und wird dort übernommen (Beanstandung → Mangel mit Nachkontrolle und Aufgabe). Ein Tag lässt sich nur einmal entscheiden; Änderungen über das Büro. Schutz: Schlüssel-Vergleich in konstanter Zeit, Begrenzung je IP (30 Anfragen / 10 Min.), Ursprungsprüfung, Tage nur bis 45 Tage zurück. Wer den Link hat, kann das Objekt abnehmen: nur an die Ansprechperson schicken.
  - Geprüft: Fachlogik (Unit-Tests), 24 neue Sicherheitschecks (Schlüssel falsch/fehlend, keine internen Daten, Doppelentscheidung, fremder Ursprung, gesperrte Verwaltungs-API), und im Browser der ganze Weg: Verwaltung → Mitarbeiter-App (Checkliste) → Übernahme → öffentliche Kundenseite → Abnahme/Beanstandung → Übernahme mit Mangel. **Nicht geprüft:** Foto-Aufnahme mit der echten Handykamera, die PDF-Ansicht in einem PDF-Programm (nur Struktur geprüft), Zustellung des Links per E-Mail (das App versendet nichts; Link kopieren und selbst senden).
- **Karte, neue Funktionen:**
  - **Ebenen (Alle Kunden):** „Offene Mängel“ hebt Objekte mit offenen Mängeln hervor (roter Rahmen, Zahl im Marker, im Popup die Zahl überfälliger); „Termine (14 Tage)“ zeigt Besichtigungs- und Starttermine.
  - **Nähe-Check:** Beim gewählten Objekt stehen die nächsten Objekte mit Entfernung (Luftlinie) und der Hinweis, wenn aktive Objekte im Umkreis von 3 km liegen (Einsätze bündeln).
  - **Tagesstand (Einsatztag):** Die Marker zeigen, ob Zeit gebucht ist, der Einsatz noch aussteht, der Beginn überschritten ist (mehr als 15 Min, keine Buchung) oder an einem vergangenen Tag keine Buchung existiert.
  - **Vertretung nach Entfernung:** Bei einem unbesetzten oder nicht voll besetzten Einsatz listet die Karte einsetzbare Personen (mit den Regeln des Vertretungs-Assistenten: Abwesenheit, Terminüberschneidung, Minijob-Grenze) nach Entfernung zu ihrem nächsten Einsatz am selben Tag, mit geschätzter Fahrzeit und „Einteilen“ (mit Rückgängig). Privatadressen sind nicht gespeichert; wer an dem Tag sonst nicht eingeplant ist, hat „Entfernung unbekannt“.
  - **Wege je Person (Touren, in den Einstellungen einschaltbar):** Km und geschätzte Fahrzeit zwischen den Einsätzen und Warnung, wenn die Pause nicht reicht.
  - **Stempel-Radius:** Ist der Standort-Abgleich eingeschaltet, zeigt die Karte beim gewählten Objekt einen Kreis mit dem eingestellten Radius.
  - Fahrzeit ist eine Schätzung (Luftlinie × 1,3, 35 km/h, 5 Min Zuschlag), keine Routenberechnung. Geprüft: Logik mit Unit-Tests, Ebenen, Nähe-Check, Tagesstatus und „Einteilen“ im Browser. **Nicht im Browser gesehen:** die Wege-Warnung (braucht eingeschaltete Touren) und der Radius-Kreis (braucht eingeschalteten Standort-Abgleich). Nicht gebaut: Position per Adresse suchen (würde Adressen an einen Kartendienst senden), Routenoptimierung.
- **Zusatzleistungen** (Geld → Zusatzleistungen): Angefragt → Beauftragt (wer beim Kunden?) → Ausgeführt (Datum) → Abgerechnet, oder Abgelehnt mit Grund; jeder Schritt im Verlauf. Ausgeführte Leistungen eines Kunden lassen sich zu **einer Rechnung** zusammenfassen (Positionen im PDF, verknüpft). Die Seite zeigt, wie viel erbracht, aber noch nicht abgerechnet ist. Wird die Rechnung storniert, sind die Leistungen wieder abrechenbar.
  - Geprüft: Fachlogik mit Unit-Tests (LV, Nachweis, Zusatzleistungen, PDF mit mehreren Positionen), die Abläufe im Browser (Prüfen mit Fehlermeldungen, Mangel aus Beanstandung, Zusatzleistung bis Rechnung, neue LV-Version mit Änderungsübersicht, Speichern auf dem Server). **Nicht gebaut:** Mitarbeiter-App hakt LV-Leistungen vor Ort ab; Kundenportal zur Abnahme; PDF des Leistungsnachweises; Zusatzleistung-Meldung durch Mitarbeitende; die Rechnungen aus Zusatzleistungen sind nicht als E-Rechnung mit Einzelpositionen aufgebaut (eine Sammelzeile).
- **Fehler gefunden und behoben (Svelte-Zustand):** Ein erstes `(x ??= []).push(…)` auf einem fehlenden Feld ging im Zustands-Proxy verloren. Betraf das Abschlussprotokoll (erster Eintrag), Korrekturanträge, Einstellungen und die neuen Listen; überall auf Zuweisung, dann Zugriff über den Proxy umgestellt.
- **Mitteilungen:** Die Mitarbeiter-App hat eine Glocke mit Zähler (und im Tab-Titel). Mitteilungen gibt es zu Tauschangeboten (nur für die, die sie übernehmen dürfen), zur Übernahme, zum Zurückziehen und zur Entscheidung des Büros; ist ein Angebot vergeben, verschwindet der Hinweis bei den anderen. Die App fragt alle 45 Sekunden und beim Zurückkehren in den Tab. Auf Wunsch zeigt sie neue Mitteilungen als Systemhinweis, **solange die App geöffnet ist**. **Kein echtes Push** (bei gesperrtem Handy oder geschlossener App): das braucht Web Push mit https, VAPID-Schlüsseln und eine Bibliothek, und ist hier nicht gebaut und nicht getestet.
- **Nicht umgesetzt:** Standortprüfung (bewusst: keine GPS-Ortung), NFC, Push bei geschlossener App, Push-Benachrichtigungen, Chat. Zwei Stempelungen innerhalb einer Minute gelten als Versehen und werden nicht gebucht.
- **Betrieb:** Der Node-Adapter begrenzt Anfragen standardmäßig auf 512 KB. Für den Datenbestand der Verwaltung `BODY_SIZE_LIMIT=26214400` setzen.
- **Was Mitarbeitende bekommen:** Der Server berechnet eine Projektion nur für die angemeldete Person (nächste Einsätze, Stundenkonto, Urlaub/Krankheit, Unterweisung). Die Person kommt aus der Sitzung, nie aus der Anfrage. Der Datenbestand, Zugänge, Preise, Rechnungen und Teamdaten werden an Mitarbeitende nicht ausgeliefert (HTTP 403, getestet).
- **Schutz:** Passwörter mit scrypt und Salt gehashed; Sitzungs-Token zufällig, im Speicher nur als Hash, Cookie `httpOnly` + `SameSite=Strict` (+ `Secure` unter https); Sperre nach 5 Fehlversuchen (15 Minuten) und Begrenzung je IP; gleiche Fehlermeldung für unbekannten Namen und falsches Passwort; Ursprungsprüfung für alle schreibenden Anfragen; Sicherheits-Header; Protokoll (Anmeldungen, Fehlversuche, Zugangsänderungen); optimistische Sperre beim Speichern (Revision).
- **Prüfung:** `npm run test:security` startet 110+ Angriffs- und Rechteprüfungen (inkl. Stempeln, Meldungen, Foto-Upload) gegen einen laufenden Server (`BASE=http://localhost:PORT`, am besten mit eigener Test-Datenbank: `RESCH_DB=/tmp/test.db`).
- **Grenzen, bitte beachten:**
  - **Nur über https betreiben** (Reverse Proxy mit Zertifikat). Ohne https können Passwörter mitgelesen werden.
  - Inhaberin, Büro und Objektleitung sehen **alle** Geschäftsdaten. Die Rollenwahl in den Einstellungen blendet nur Menüpunkte aus.
  - Keine Zwei-Faktor-Anmeldung, kein „Passwort vergessen“ (Inhaberin erzeugt einen neuen Code), kein Datenschutz-Audit, keine Penetrationstests durch Dritte. Vor dem Echtbetrieb prüfen lassen.
  - Das **Kundenportal** (`/portal/<id>`) ist nur noch eine Vorschau für angemeldete Verwaltungsnutzer. Ein öffentlicher Zugang für Kunden braucht eigene Zugangsdaten und einen eigenen, eingeschränkten Endpunkt.
  - Die Datenbank `data/resch.db` enthält echte Daten: sichern, nicht einchecken (steht in `.gitignore`). Für größere Betriebe ist PostgreSQL vorgesehen.
  - Der Datenbestand liegt als ein Dokument auf dem Server und wird vom Browser der Verwaltung gespeichert; Mehrbenutzerbetrieb wird nur durch die Revisionsprüfung abgesichert (bei Konflikt: neu laden).

# Objektia (Prototyp)

Interaktiver Frontend-Prototyp. **Alle Daten sind erfundene Demo-Daten**, sie liegen nur im Browser (localStorage). Es gibt noch kein Backend, keine Datenbank und keine Anmeldung. Das kommt in Phase C.

```bash
npm install
npm run dev      # http://localhost:5173
npm run check    # TypeScript / Svelte
npm test         # Unit-Tests: Rechenlogik, PDF-Erzeugung (Vitest)
npm run build    # Produktions-Build (adapter-node)
```

"Demo zurücksetzen" in der Seitenleiste lädt die ursprünglichen Demo-Daten neu. ## Nicht umgesetzt / Einschränkungen

- Kein Backend, keine Authentifizierung, keine Berechtigungen, keine Datenbank.
- Kein E-Mail-Versand, E-Rechnung nur als ungeprüfte Dateien (siehe oben). PDFs entstehen im Browser mit Standardschrift Helvetica.
- Absenderdaten in `src/lib/company.ts` sind Platzhalter (Demo).
- Feiertagskalender nur bundesweit (Landesfeiertage fehlen), Nachtzeit 23–6 Uhr ist eine Annahme. Keine GPS-Erfassung, bewusst.
- Tarifwerte, Leistungswerte, Ampelgrenzen und Standard-Vertragslaufzeiten sind Annahmen und Szenarien (Stand 02.11.2026), keine Rechtsauskunft. Mahn- und Briefvorlagen vor Einsatz rechtlich prüfen.
- Das Kundenportal ist eine Vorschau mit lokalen Daten: ohne Backend gibt es keinen Zugriffsschutz und keine öffentliche Erreichbarkeit.
- Noch offen: Leistungsnachweis/Arbeitsschein mit Unterschrift, zentrale Tarifparameter-Tabelle mit Gültigkeit, Plan-Editor mit Ruhezeit-Warnungen, mehrsprachige Mitarbeiteransicht, Dateiablage. Dialoge Einstellungen, CSV-Import, Einsatzzettel und Tagesbriefing sind bisher nur über Typprüfung und Build abgesichert, nicht per Browser-Test.
- Bewusst nicht gebaut (laut Recherche rechtlich heikel oder aufwändig): Dauer-GPS, Pflicht-Geofencing, personenbezogene Scores, eigene Lohnabrechnung, Bank-API.
- Playwright-Kernabläufe, Responsive- und Tastaturprüfung stehen aus. Getestet wurden bisher Rechen- und PDF-Logik (Vitest) sowie die Hauptabläufe manuell im Browser.
